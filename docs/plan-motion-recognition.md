## 기술 선택 (자세한 이유는 `docs/decisions.md`)

**설치**
- MediaPipe **1.0.0**의 몸 인식 기능 PoseLandmarker를 영상 모드(VIDEO)로 씁니다. 처음에는 1.0.1로 정했으나, 1.0.1은 맥에서 몸 인식이 강제 종료되는 버그가 있어 10/4에 1.0.0으로 바꿨습니다(`docs/decisions.md`).
- 파이썬 3.11. 가상환경(이 프로젝트 전용 부품 설치 공간)은 `motion/.venv`. 팀원은 python.org에서 3.11.9를 설치합니다(설치 프로그램으로 받을 수 있는 마지막 3.11).
- 설치 목록(`motion/requirements.txt`)과 모델 파일 주소는 정확한 버전으로 고정합니다.
- **실행 방법(모든 팀원 공통)**: 운영체제별 더블클릭 파일 한 쌍. 처음 한 번 `setup`, 그 뒤로는 `run`.
  - 윈도우: `setup.bat` / `run.bat`
  - 맥: `setup.command` / `run.command`
  - 파일 안에서는 가상환경의 파이썬을 직접 부릅니다. 윈도우 PowerShell이 기본 설정에서 가상환경 켜는 명령을 막기 때문입니다.
- 레포는 ZIP이 아니라 git으로 받습니다. ZIP으로 받으면 맥이 `.command` 실행을 막습니다.
- 맥 조건: Apple 칩(M1 이후), macOS 13 이상. 처음 실행할 때 터미널의 카메라 접근을 허용해야 합니다. 맥에서는 카메라 방식을 자동으로 맥용으로 바꿉니다.

**확인 화면**
- OpenCV 창. 화면 글씨는 영어(OpenCV 기본 글꼴은 한글을 못 씀).
- 화면의 LATENCY는 **처리 지연**입니다: 사진을 받은 순간부터 화면에 그리기 직전까지. 카메라와 모니터 자체의 지연은 빠져 있어서, 전체 지연은 휴대폰 슬로모션 촬영으로 따로 잽니다.
- 화면 숫자는 1초 평균. 프로그램을 끌 때 터미널에 보통 값(중간값)과 가끔 느려질 때의 값(가장 느린 5%)을 찍습니다.

**동작 판정**
- 왼쪽·오른쪽은 체험자 본인 기준(화면은 거울처럼 보여 줌).
- 동작 하나는 "여러 상태 중 하나"입니다(기울이기 = 왼쪽/오른쪽/없음). 서로 다른 동작은 동시에 켜질 수 있고, 아무것도 없으면 NONE.
- 기록과 떨림 방지 상태는 "사람 자리"별로 관리합니다(지금은 자리 0 하나).

## 1단계: 카메라 창 + FPS + 지연 표시 (인식 없이 카메라만)
- 볼 것: 거울처럼 보이는 내 모습, 왼쪽 위에 `CAMERA 30 fps · LOOP 30 fps · LATENCY 15 ms · 640x480 MJPG DSHOW`(카메라가 실제로 주는 값). q로 끄면 터미널에 요약.
- **성공 기준**: 창이 5초 안에 뜸 / CAMERA 25 fps 이상 / 손을 빠르게 흔들어도 영상이 바로 따라옴. 어두우면 fps가 떨어질 수 있으니 밝은 곳에서 확인.
- 비교: 해상도 640×480과 1280×720, 윈도우 기본 카메라 방식(MSMF)은 한 번만.
- 10/4 sunbell 노트북 측정
  - 카메라는 640×480이 최대라 1280×720 비교는 할 수 없음
  - 3분 반 시험(sunbell 실행)
    - MSMF: CAMERA 평균 30.0, LOOP 29.7 fps, 처리 지연 보통 0 ms·느린 쪽 5% 2 ms, 여는 데 1.3초
    - DSHOW: CAMERA 평균 29.4, LOOP 29.3 fps, 처리 지연 보통 0 ms·느린 쪽 5% 1 ms, 여는 데 3.5초
    - 둘 다 멈추지 않았음
  - 3초 짧은 시험(Claude 실행): DSHOW만 초당 8~16장으로 낮았다. 켠 직후 몇 초 동안 느린 것으로 보인다(추측)
  - 처리 지연이 0 ms인 이유: 아직 화면을 뒤집는 일만 해서 0.5 ms도 안 걸리기 때문. 2단계부터 의미가 생긴다

## 2단계: 몸 뼈대 표시
- 볼 것: 몸 위에 점과 뼈대 선, 화면 밖으로 나가면 `NO PERSON`, `INFER xx ms`, `MODEL lite`
- **성공 기준**: 뼈대가 몸을 잘 따라다님 / 나가면 1초 안에 NO PERSON / LATENCY 평균 100 ms 이하(시작 목표) / 2~3 m 떨어져 두 팔을 들어도 손목이 화면 안에 들어옴
- 비교: `--model lite`와 `--model full`. (정보용) `--num-poses 4`로 여러 명 설정 시 속도와 흔들림 → 팀의 "동시 4인" 결정 자료
- 결정: 기본 모델

## 3단계: 동작 판정 틀 + 샘플 동작 2개
- 규칙 초안(시작값)
  - ARMS_UP: 두 손목이 모두 코보다 위면 켜짐, 한 손목이라도 어깨 아래로 내려가면 꺼짐. 손목이 화면 위로 벗어나도 "든 것"으로 침
  - LEAN: 두 어깨를 잇는 선의 기울기(실제 화면 픽셀 기준). 12° 이상이면 켜지고 7° 아래로 가야 꺼짐. 결과는 왼쪽/오른쪽/없음
- 볼 것: 큰 글씨의 동작 이름, 지금 각도와 켜짐·꺼짐 기준선이 표시된 기울기 막대
- **성공 기준**: 두 팔을 들면 곧바로 ARMS_UP, 내리면 사라짐 / 기울이는 방향대로 LEAN_LEFT·LEAN_RIGHT, 바로 서면 NONE / 좌우가 반대로 뜨지 않음
- 확인할 위험: 한 팔만 들어도 어깨가 기울어 LEAN으로 잘못 뜰 수 있음 → 문제가 되면 몸통 기울기(어깨 가운데와 엉덩이 가운데를 잇는 선)로 바꾸는 방안
- 결정: 기울기 기준 각도, 여러 동작 동시 표시가 괜찮은지
- README에 "새 동작 추가하는 방법"

## 4단계: 떨림 방지 + 사람 없을 때 처리
- 볼 것: `RAW`(원래 결과, 작은 글씨)와 `STABLE`(떨림을 막은 결과, 큰 글씨), 최근 몇 초의 변화를 보여 주는 색 띠
- 시작값: 기울이기 0.1초 유지되면 켜짐/0.15초 사라지면 꺼짐, 두 팔 들기 0.15초/0.25초, 사람이 0.5초 이상 안 보이면 NONE
- **11/5 확정**(sunbell): 기울이기 0.20초/0.25초, 두 팔 들기 0.25초/0.35초, 사람 없음 0.5초(그대로)
- 알아 둘 점: 기다리는 시간만큼 반응이 늦어짐(안정성과 빠르기는 맞바꾸는 관계)
- **성공 기준**: 경계 각도에서도 STABLE이 깜빡이지 않음 / RAW가 한 번 튀어도 STABLE은 그대로 / 나가면 1초 안에 NONE / 굼뜨게 느껴지지 않음
- 결정: 대기 시간

## 5단계: 속도 다듬기 + 마무리 확인
- 시험 조건: 노트북 전원 연결, 전원 모드 "최고 성능", 부스와 비슷한 밝기
- 해상도·모델 조합별 FPS와 지연(보통 값, 느린 쪽 5%) 비교표 → 기본값 확정
- 휴대폰 슬로모션으로 옛 프로그램과 새 프로그램의 전체 지연 비교
- **성공 기준**: MediaPipe 담당이 직접 보고 "됐다" → 첫 번째 목표 완료

## 첫 번째 목표 마무리 확인 방법
1. 기본 설정으로 실행하고 카메라에서 2~3 m 떨어져 섭니다.
2. 각 동작을 5번씩 합니다. 매번 맞는 이름이 뜨는지, 깜빡임이 없는지, 화면 밖으로 나가면 NONE이 되는지 봅니다.
3. 터미널 요약에서 FPS 25 이상, 처리 지연 100 ms 안팎인지 봅니다(시작 목표).
4. 휴대폰 슬로모션으로 찍은 전체 지연이 옛 프로그램보다 확실히 짧은지 봅니다.

## 11/11 발표회용 글자 보내기

11/11(수) 학과 발표회에서 몸 동작으로 차를 움직이는 모습을 보여 줘야 합니다(팀 안건 「운영 7 · 11/11 발표회 시연」). 그래서 5단계보다 먼저 합니다(11/8 sunbell).

**정해진 것**
- 글자 약속: `F` = 앞으로, `S` = 멈춤. 차는 `F`를 받으면 정해진 시간만 가고 스스로 멈춥니다. 아두이노 코드는 블루투스와 USB 양쪽에서 같은 글자를 받습니다(11/8 sunbell, 자세한 것은 팀 결정 기록).
- 몸 동작과 보내는 때: 두 팔 들기가 켜지는 순간 `F`를 한 번, 프로그램을 끌 때 `S`를 한 번(11/8 sunbell, `docs/decisions.md`).

**아직 정하지 않은 것**(팀 안건 「운영 7 · 11/11 발표회 시연」): `F`를 받고 몇 초 갈지, 언제 모여 이어 볼지, 예비책.

**쓰는 법**: 더블클릭으로 실행하면 글자를 보내지 않습니다. 보내려면 `run.bat --port COM5`처럼 포트를 적습니다. 자세한 것은 `motion/README.md` 6번을 봅니다.

**시험표**

| 단계 | 필요한 것 | 확인할 것 | 하는 사람 | 결과 |
|---|---|---|---|---|
| 1. 자동 시험 | 없음 | 한 번 들면 `F` 1번, 떨려도 1번, 못 보낸 글자는 버림, 포트 오류에도 안 꺼짐, `pyserial`이 없어도 켜짐 | Claude | 22개 통과(11/8) |
| 2. 화면 시험 | 웹캠 | 팔을 들면 화면 `OUTPUT` 줄의 `sent`가 1 늘고 터미널에 `[가짜 보내기] F`가 나옴 | sunbell | 따로 하지 않음. 실제 블루투스 시험(4·8단계)에서 같은 것을 확인함(11/11) |
| 3. 가상 포트 | `pyserial` | 보낸 글자가 되돌아오는 가상 포트(`loop://`)에서 `F`가 돌아옴 | Claude | 통과(11/8) |
| 4. 실제 블루투스 | sunbell 키트 | 짝 맺기, 나가는(Outgoing) 포트 찾기, 화면에 `OPEN`이 나옴 | 함께 | 통과(11/11). HC-06 짝 맺기는 아두이노 세션이 함. 나가는 포트는 `COM11`. 보내기 코드로 열면 1.0초 만에 `OPEN` |
| 5. 보드 도착 확인 | sunbell 키트, 키트의 앱 조종 예제 | 블루투스로 보낸 `F`가 USB 쪽으로 되돌아옴. 이 예제는 받은 글자를 USB로 되돌려 보내고 대문자 `F`에는 모터가 반응하지 않습니다(예제를 읽어 안 사실, 실제로 해 보지는 않음) | 함께 | 키트 예제 대신 아두이노 담당의 새 코드로 확인함(11/11, 아두이노 세션). 이 코드도 받은 글자를 USB로 `BT: F -> 앞으로`처럼 되돌려 찍음 |
| 6. 키트 예제로 차까지 | sunbell 키트, 키트의 앱 조종 예제 | `--letter-on g --letter-off s --letter-quit s`로 실행해서, 팔을 들면 차가 가고 내리면 멈추는지 봄(글자 순서는 가상 포트에서 확인함, 차로는 안 해 봄). 이 예제는 스스로 멈추지 않으니 처음에는 바퀴를 띄워 시험합니다. 11/8 약속(`F`, 스스로 멈춤)과 다른 시험 전용 설정이고, 예비책으로 쓸지는 아직 정하지 않았습니다 | 함께 | 하지 않음. 아두이노 담당의 새 코드가 준비되어 그 코드로 바로 시험함(11/10 sunbell 결정, 총괄 세션이 전함) |
| 7. USB 선 | sunbell 키트 | 포트만 바꿔서 같은 시험. 포트를 열 때 보드가 다시 켜져 처음 글자를 놓치는지 봄(짐작, 안 해 봄) | 함께 | 아직. 예비책(`run.bat --port COM9`)이지만 몸 동작 프로그램으로는 해 보지 않음 |
| 8. 실제 차 | 아두이노 담당의 새 코드 | 팔을 들면 차가 정해진 시간만 가고 멈춤 | 함께 | 통과(11/11, sunbell 차, 블루투스 `COM11`). 바퀴를 띄우고 4가지 확인(`OPEN`, 들 때 한 번, 다시 들면 또 감, `q`로 `S`). 바닥에서 팔을 5번 들어 `F` 5번 보냄, 버린 글자 0, 차 5번 모두 움직임. 28.5 fps, 처리 지연 보통 22 ms. 차에는 담당자 코드(`aa7ae28`)에서 세기만 255로 바꾼 판이 올라가 있음 |
| 9. 시연 장소 확인 | 발표회 장소나 비슷한 곳 | 노트북 전원을 연결한 상태의 속도, 거리와 밝기, 뒤에 사람이 있을 때 다른 사람을 잡거나 잘못 켜지지 않는지 봄. 지금까지의 시험은 사무실에서 혼자 한 것입니다 | sunbell | 일부 통과(11/11 리허설). 팔을 내린 채 146초 동안 뒤로 사람이 지나가게 함: 두 팔 들기와 기울이기가 한 번도 켜지지 않음. 29.6 fps, 처리 지연 보통 19 ms. 전원 연결 여부와 실제 발표장에서는 확인 못 함 |

키트 예제 코드는 읽어서 사실만 확인하고, 옮겨 적거나 레포에 올리지 않습니다.

## 두 번째 목표: 값으로 표현 (큰 흐름만)
- 흐름: 인식(동작 판정, 떨림 방지) → 값 만들기(예: `mapping.py`) → 내보내기(`output.py`: 화면, 콘솔, 테스트용 가짜 출력)
- 아두이노로 실제 전송하는 부분은 11/11 발표회용으로 먼저 만들었습니다(11/8, 위 「11/11 발표회용 글자 보내기」). 이음제에서 쓸 값의 약속(무슨 값을 얼마나 자주)은 발표회 결과를 보고 정합니다(팀 안건 「개발 2 · 내보낼 값」).
- 값 표현 후보(명령어 방식 / 숫자 방식 / 섞은 방식)를 자동차 예시로 비교하고, 콘텐츠가 바뀌어도 쓸 수 있는지 평가합니다.
- 고른 뒤 통합 담당용 값 명세 문서(`docs/value-spec.md`)를 씁니다. 세부 계획은 첫 번째 목표 확인 뒤에 다시 세웁니다.

## 미리 고려만 해 두는 것 (지금 만들지는 않음)
- 여러 명: 결과를 "사람 목록"과 "사람 자리"로 다룸. 4명 동시가 필요해지면 누가 어느 자리인지 정하는 규칙만 추가(예: 바닥 칸으로 구분). MediaPipe는 사람마다 ID를 주지 않음.
- 반복 동작: 최근 약 2초 기록을 시간 기준으로 볼 수 있음. 제자리 달리기 등은 규칙 파일 추가로.
- 부스에 사람이 많을 때: 뒤에 서 있는 사람을 잡을 수 있음 → 필요하면 "체험 구역"만 잘라서 봄.
- 손 인식: 필요해지면 `pose.py` 옆에 손 인식 파일을 추가.
